## Rendering and boss size

The renderer reduces repeated CPU work and draw submissions without lowering approved geometry detail, PBR materials, render resolution, shadows or motion-channel coverage:

- The optimized rig writes each deformation directly from its captured rest surface, avoiding an immediate restore that the same field would overwrite. Unchanged output can retain its computed normals. Conservative bounds are collected during the existing vertex pass; an unused field still restores exact authored positions and normals.
- Same-source, same-clock, same-mode enemy peers reuse an evaluated pose through private buffer copies. Independently decoded sources and structural variants remain separate. Defender cooldowns and attack phases remain individual. The existing unchanged-clock freeze behavior is retained.
- Compatible basic-defender surfaces share private skeletal material batches, retaining exact skin attributes, bind matrices and original material objects. Named original surfaces remain available for anchors and inspection; disposal removes private batches and restores original layers before skeleton cleanup.
- An unchanged viewport no longer reallocates the drawing buffer or recomputes the projection on every UI render. Real viewport changes still resize and retain the player's camera.
- Every boss receives **0.84× its previous presentation scale**, a 16% reduction on each axis, including idle/death presentation. Ordinary units, health, combat ranges, targeting, navigation and collision rules are unchanged.

The [render proof](../output/design/ipad-performance-v047-20261019/render/render-proof.json) records comparison against preserved motion sources: exact positions/normals, world transforms and visibility across eight time/mode samples on all 92 champion/enemy sources; every posed skinned vertex, shader normal, original attribute/material and bind matrix at four attack phases on all 48 basic models; and private peer-copy checks on all 54 enemy identities. These sampled equivalence checks do not certify every possible pose/contact cycle.

## Measurements and their limits

The [refreshed CPU benchmark](../output/design/ipad-performance-v047-20261019/render/cpu-motion-benchmark.json), reproduced by `tools/benchmark-render-v047.mjs` after the cache correction below, uses actual approved GLTF sources and matching motion samples in local Node. Recorded 12-peer crowd results are:

| Model | 0.4.6 CPU milliseconds per crowd frame | Optimized CPU milliseconds per crowd frame | Local CPU speedup |
| --- | ---: | ---: | ---: |
| Spectral Dual-Seal Inquisitors (`host_31-wraith`) | 5.619 | 0.624 | 9.01× |
| Blood-Leech Trolls (`host_38-wraith`) | 71.316 | 6.430 | 11.09× |

Across the recorded crowd repetitions, 2,160 field evaluations become 180 evaluations plus 1,980 private pose copies. These are **CPU operation counts**, not draw calls. Across all 48 isolated basic profiles, the benchmark counts 8,249 original mesh objects and 2,087 render-layer-enabled mesh objects after batching, approximately 74.7% fewer submission candidates, with no triangle reduction. That is a CPU-side submission estimate for the recorded actors, not a measured whole-battlefield `renderer.info.render.calls` result; actual passes, material groups, culling, shadows and other scene objects affect the latter.

CPU timings are sample-dependent and sensitive to host load; this refreshed run may overlap the final test/build process. These results exclude browser scheduling, GPU time, rendering throughput, thermal behavior and physical iPad performance. They must not be converted into an iPad FPS promise. The [0.4.6 baseline capture](../output/design/ipad-performance-v047-20261019/baseline-046-native.json), [running-window diagnostics](../output/design/ipad-performance-v047-20261019/baseline-046-running-native.json) and [baseline image](../output/design/ipad-performance-v047-20261019/01-baseline-046-wave38.jpg) use desktop Chromium at a tablet viewport with a controlled wave-38 army. ## Independent cache finding and correction gate

An independent read-only review found that a cache row referenced a mutable owner without confirming that the owner still held that row's pose. Reproduction on the actual Blood-Leech Troll source: actor A walks at time 0.2, then rests at 0.4; a new peer B requesting walk at 0.2 incorrectly receives A's current rest pose. Same-clock, monotonic peer tests passed, so they did not cover this seek/out-of-order-clock case.

<!-- V047_CACHE_CORRECTION_VERIFIED -->
**Correction verified.** Each cache row now records the mutable rig's exact `poseRevision`; evaluation, joint/field writes, reset and copy receipt advance that revision. A changed owner invalidates reuse. The [correction receipt](../output/design/ipad-performance-v047-20261019/render/cache-correction.json) and refreshed render proof record **35 passed, zero failed**, covering seven real-source seek/mode/copy-recipient/reset scenarios and unchanged 0.4.6 same-clock behavior. An independent rerun of the original A-walk/A-rest/B-walk reproduction now returns B's correct requested walking pose. Initial render proof, CPU timings and focused logs remain preserved as `*-initial` receipts. The final full test/build gate remains separate below.
